# dsh-turn-nav vs dsh 官方 TurnNavigator 对比与调整方案

> 生成日期：2026-08-29。基于 dsh 0.1.2-alpha.1 源码（`packages/client/ui-chat`）。
> 目的：全面对比官方内置"轮次胶囊条"与 dsh-turn-nav 插件，定位冲突原因，给出调整方案（仅方案，未改动）。

## 一、冲突原因（为什么"只显示官方的"）

1. **官方 rail 内嵌于 ChatView**（`ui-chat/src/client/chat/TurnNavigator.tsx`），是会话视图的**内置组件**，无开关、始终渲染。
2. **我们的 rail 注册于 `conversation.session.header.utilities`**（`position: fixed`，全屏右侧）。
3. **两者都定位在"右缘垂直居中"**：
   - 官方：`.slot` sticky + `.rail` `top: band/2; right: ~28px; width: 28px`
   - 我们：`.tn-wrap` `fixed; right: 6px; top: 50%; width: 26px`
   → **位置重叠**。用户视觉上只看到官方（官方在 transcript 滚动容器内、随内容稳定；我们的 fixed 与之叠在几乎同一位置），或我们的被官方遮蔽/视觉混乱，表现为"冲突，只显示他们的"。
4. 若用户实例**没加载我们的 bundle**（profile 未装/未生效），则纯因未加载而"只显示官方的"——需用户侧确认。

## 二、功能对比（官方 vs 我们）

| 维度 | 官方 TurnNavigator | dsh-turn-nav（我们的） |
|---|---|---|
| **位置** | transcript 内 sticky（右缘，随滚动区域，z-index 6） | header.utilities fixed（全屏右缘，z-index 10） |
| **数据来源** | `ChatTurnNavigationIndex.items()`——**仅窗口内已加载 turns** | `sessions.history` RPC **全量持久化轮次** + 窗口补充 |
| **覆盖轮次** | 只有已加载进窗口的轮次；更多历史靠滚动顶部/点"加载更早"扩展 | **全部轮次即时可见**（含窗口外），无需 prepend |
| **跳转窗口外轮次** | ❌ 无——items 里没有窗口外 mark，看不到也跳不了 | ✅ 有——点击窗口外轮次自动按需扩展窗口（带"正在定位第 N 轮…"反馈） |
| **打开会话性能** | 窗口渲染（正常） | **零 prepend**（history-as-data，不重渲染 flow），长会话不卡 |
| **mark 视觉** | 比例分布（index/(count-1)），tick 2px 高、12→18→20px 宽，右对齐 | 等高胶囊（3px 高、12px 宽），竖排，hover 变主题色+向左加宽 150%（波浪） |
| **hover 预览** | prompt + response 双行（各 ≤160 字符，clamp 2 行，300px 宽/100px 高） | 左侧 tooltip（序号 + 时间 + 完整摘要，pre-line 多行，动态测量保证视口内） |
| **active/跟随** | ✅ 跟随滚动（`turnAtLine` 阅读线 + rAF） | ❌ 无（我们没做跟随滚动高亮） |
| **键盘可达** | ✅ mark 是 button，focus-visible 有焦点环 | ⚠️ 按钮可达但无专门 focus 视觉 |
| **滚动按钮** | ❌ 无（比例压缩，长会话 mark 密集） | ✅ 上下按钮（点击 + hover 自动滚动 + 置灰） |
| **高度** | 固定 band 内按比例压缩（最高 420px） | 自适应（≤30vh）+ 内部滚动 |
| **窄窗口** | `@container (max-width:900px)` 自动隐藏 | 无隐藏 |
| **加载反馈** | 无（跳窗口内即时，无等待场景） | ✅ 窗口外跳转有反馈（脉冲 + 气泡） |
| **最老轮次** | 无特殊处理（不保证加载到底） | ✅ 点击最老轮次加载到 hasMore=false（真正第一轮） |

**结论**：官方主打"当前窗口内快速定位 + 阅读跟随"，实现简洁、性能好（memo + 比例分布）；我们在**全量历史可见、窗口外按需跳转、长会话性能、滚动按钮、加载反馈**上明显更强。用户感知"官方效果没我们好"主要因官方**看不到窗口外轮次**。

## 三、需要用户确认的事实

1. 用户实例（看到的界面）**是否加载了 dsh-turn-nav**？→ 决定是"位置冲突"还是"未加载"。
2. 用户更喜欢哪个定位交互（官方跟随滚动 vs 我们的滚动按钮）？→ 决定融合方向。

## 四、调整方案（候选）

### 方案 A：共存差异化（推荐做最小改动验证）
- 我们的 rail **换位置**避开官方：官方在 transcript 右缘（`right` 贴近滚动条），我们可挪到 **header.utilities 固定、但偏上/或贴近右缘更外**（如 `right: 34px` 避开官方 28px 列）或 **改成右上角胶囊**。
- 或**接受官方 rail 占位，我们只保留官方没有的能力**：把我们的 rail 收缩为"官方不可达的窗口外轮次 + 按需跳转"的补充工具（例如只在有窗口外轮次时才出现）。
- 优点：两个都能用，发挥各自优势；缺点：两个 rail 并存仍显冗余。

### 方案 B：只保留一个
- **B1 用官方的**：卸载/停用 dsh-turn-nav，接受官方能力（窗口内定位 + 跟随），丢失窗口外按需跳转/长会话零 prepend 优势。
- **B2 用我们的**：官方 rail 无开关无法从插件移除（内嵌 ChatView）——只能**改 dsh 源码**（违背"不改 dsh"原则）或建议官方提供开关。不可行（插件立场）。

### 方案 C：我们补齐官方缺失、成为"官方增强层"
- 保留我们的 history-as-data 数据层，**UI 融合官方风格**：
  - 我们 rail 改到官方**不占的位置**（如左侧/更右），或在官方 rail 之上叠加"窗口外轮次"标记（仅显示官方 items 之外的轮次，点击按需加载）。
  - 增加**跟随滚动高亮**（对齐官方能力，弥补我们缺失项）。
  - 增加 **900px 窄窗口隐藏**（对齐官方）。
- 本质是"官方 rail + 我们的全量数据/按需加载"融合成**单一 rail**。

### 方案 D：等官方开放
- 官方无开关是当前版本事实；若后续官方支持禁用/自定义，我们可提供"替换官方 rail"的注入（如果官方给 slot/开关）。

## 五、建议

1. 先确认事实 1（我们 bundle 是否加载）——若没加载，先解决加载（profile/兼容），"冲突"即不成立，回到"我们的 rail 单独工作，只是和官方重叠"。
2. 若确实共存冲突，推荐 **方案 C**：把我们的 rail 改造成"官方增强层"——复用官方位置思路，但数据全量 + 窗口外按需跳转 + 反馈 + 滚动按钮，且**在官方 rail 可见时自动避免重叠**（如我们只显示窗口外轮次，或整体让位）。
3. 在动手前，先小范围验证：把我们的 rail 临时挪位（如 right: 40px）看是否与官方共存清晰，再决定融合深度。
